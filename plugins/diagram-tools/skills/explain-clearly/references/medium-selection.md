# Choose a medium for the question

Start with the audience, the distinction they need to understand, and the
available evidence. Infer these from the request and context when clear; ask
only when the missing information changes the result. Do not make a simple
answer into an artifact project.

| Need | Owner and output |
| --- | --- |
| One result, definition, or simple procedure | Prose or a short list; no rendering runtime |
| Three or more comparable entities or repeated fields | Markdown table |
| Components, boundaries, or a fixed flow | Archify; explicit Mermaid or compact static relationships use Pretty Mermaid |
| Inspect how changing an input changes state or results | Bundled Visualize in the conversation; useful controls and a visible current state |
| Follow a requested explanation over time | Installed Remotion; editable composition and Studio preview; export only when requested |
| Measured results for a paper | Paper Figure Workflow; source data, plotting code, SVG/PDF and regeneration command |
| Native editable drawing | The requested or established OmniGraffle/Draw.io owner |
| Standalone or hosted application | Project files or Sites |

These are selections, not successive stages. A source-backed text answer can
be complete. An interaction should expose a causal dependency or a meaningful
inspection task, not merely decorate a static answer. A video is appropriate
when requested; do not substitute one for a user-controlled exploration.

## Handoff without duplicating implementations

Pass the selected owner the audience, question, inspected sources, facts and
uncertainties, relevant inputs, operations, and expected outputs. Include one
small traceable example when useful. Keep a stable vocabulary and units across
the explanation and artifact. Label schematic or synthetic values at the point
of use; do not turn a visual reference into evidence for system behavior.

Resolve bundled Visualize and installed Remotion from the current skill catalog,
then read the selected owner's active skill. Never assume a cache version or
copy its implementation into this plugin. If the owner is unavailable, disclose
the limitation and preserve useful source material. A storyboard is not a
rendered video, a static diagram is not an equivalent interactive simulation,
and an HTML file is not proof of a successful preview.

For requested video, prepare a short sequence of sourced states/events and then
delegate composition, timing, layout, preview, and explicit export to Remotion.
Preserve editable project source. Use a concise text alternative and captions
when there is speech. Verify scene order, labels, units, and the first/final
states. Do not introduce generated factual imagery, paid media, external
narration services, or hosting without the required authorization.

For a requested preview or technical qualification, use the owner's supported
preview. If its in-app browser is unavailable, disclose that fact and inspect
the exact local preview URL in the user's available browser when browser
inspection is authorized. Keep Remotion's preview server and exact URL for its
required handoff; do not report that fallback as an in-app browser check. For
Visualize, distinguish its bundled sandbox preview from final inline host
delivery. A sandbox preview does not prove that a final chat attachment rendered.

The `diagram-tools` plugin's display name is Visual Communication. It owns this
handoff and the publication pipeline, not the external Visualize/Remotion
implementations or native application permissions. Archify remains the only
automatic caller of Diagram Publish; its installation-specific sharing opt-in
does not apply to other media. Keep generated previews and cleanup with their
owning skills; preserve active handoffs and explicitly requested open results.
